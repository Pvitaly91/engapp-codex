# Gramlyze: порядок роботи

- На початку коротко підсумуй завдання та його межі; працюй саме в Gramlyze.
- Реалізацію й HTTP/браузерні перевірки виконуй на `http://gramlyze.loc`; production-профіль перевіряй ізольованими локальними тестами.
- Після завершення завдання на зміни перевір результат, зроби commit і push пов’язаних перевірених змін у робочу гілку, якщо користувач явно не наказав інакше. Дотримуйся PR-only політики `main`.
- Деплой потребує окремого дозволу. Commit/push самі по собі не дозволяють деплой.
- Не коміть секрети, `.env`, runtime caches, дампи/backups, приватні діагностичні дані або сторонні незавершені зміни. Явно обирай файли/hunks і перевіряй staged diff.
- Для погоджених змін контенту редагуй versioned sources і застосовуй їх до перевіреної робочої локальної БД `gramlyze.loc` після preview та резервного копіювання; повторне підтвердження вже погодженого локального scope не потрібне. Завершення потребує перевірки реальних сторінок: fixture/DOM-preview не замінює локального apply. За конфлікту даних, невизначеної цілі чи недоступного середовища не форсуй зміни й явно зазнач невиконаний крок. Це не дозвіл на production-деплой, зміну `.com`/`.ub`, масове пересівання чи сторонні зміни; аудит/аналіз не дозволяє запис у БД. Apply виконуй у межах конкретного завдання, без автоматичних HTTP/startup/hooks/scheduler механізмів.
- За готового авторського payload виконуй лише технічне перенесення й перевіряй незмінність копії; змістові правки потребують окремого погодження.
