### Actual CGI, OPcache та process CPU

Фактичний вебпроцес — Windows `php-cgi.exe`, PHP 8.5.10, SAPI `cgi-fcgi`. В усіх чотирьох профільованих GET один і той самий worker (`W1`: alias PID + executable/config context), один executable і один завантажений INI; додаткових INI — 0. Xdebug, Blackfire, Tideways/XHProf, Excimer, SPX, New Relic та Zend Debugger не виявлено. Це не PHP-FPM і не вимірювання CLI OPcache; для всіх GET A/A ідентичність worker лишається unknown.

## Один кандидат — точна належність перед перевіркою пакета Conditionals

Вимірюване ранжування на швидших зразках: (1) Blade 1904–2552 мс, зокрема ~1197–1204 мс widget projections без зміни результату; (2) решта controller поза Blade 131–193 мс; (3) поза controller 48–369 мс, склад не до кінця встановлено. Completed SQL 97–105 мс перетинається з етапами вище, не окремий доданок. Рендер потрібен; перевірка належності для іншої теми — найкраще місце перевірити зайву роботу. Особливо довгі профілі показують більший невстановлений wall-over-CPU залишок, а не більший надійний потенціал оптимізації.

`ConditionalsWidgetHints::project()` ([source](../../app/Support/ConditionalsWidgetHints.php#L64)), який викликає [канонічний компонент практики](../../resources/views/components/text-block-practice-questions.blade.php#L175), — найбільша виміряна група no-change із власним дорогим ланцюжком у цих двох уроках. `project()` → `load()` (5 разів/GET, на кожному наявна outer SHA/path перевірка) → `validate()` (1 раз/GET) → `ConditionalsPracticeSupplement::load()` → `ConditionalsPracticeSource::deriveTargets()` (синтетична побудова 13 цілей). Для `project()` кожний із 5 викликів повернув той самий payload на всіх чотирьох GET. Для `validate()` це вимірювання часу роботи, **не** доказ, що кожна з п’яти пар точно відсутня в контракті: збіг міг бути відхилений пізнішим snapshot guard.

**Наступний кодовий крок (не реалізовано):** тільки в сім’ї Conditionals додати точну перевірку пари `(blockUuid, questionId)` перед дорогою побудовою/валідацією тематичного пакета, використовуючи попередньо підготовлений реєстр **13 UUID і 65 пар**, виведений із того самого SHA-pinned контракту. Спочатку окремим preflight без публікації IDs підтвердити, що фактичні пари обох уроків — промахи. У майбутньому коді скорочувати шлях лише для **доведено чужої пари** після чинної перевірки файла на існування, symlink і SHA; звірити, що SHA закріплює саме ту версію, з якої побудовано реєстр, і що target list та question rows дають точну однакову множину. Якщо доказ неповний, реєстр відсутній/розходиться чи форма даних сумнівна — повний поточний шлях або той самий fail-closed результат, що сьогодні. Для відповідних пар зберегти всі transitively pinned source guards і exact matching (caller, UK, type 4, question/answers/options/hints/aliases snapshots). Не замінювати перевірку ключем slug, за темою чи seeder і не змінювати спільний renderer, selection, scoring чи інші сім’ї.

**Межа, не обіцянка:** gross ceiling гілки `validate()` на двох швидших профілях — **~183 мс PPC / ~268 мс Word Order** (8,8% / 8,6% PHP ready), якщо підтвердяться промахи. Реальна економія менша після guard/lookup і з урахуванням інструментації; якщо для еквівалентності потрібна та сама повна перевірка, економію не встановлено. 563–1613 мс у повільних профілях не прогноз; self та incl не додаються. На тлі 84–113 мс медіанного парного шуму і 148–166 мс міжблокового руху одиничний замір такого масштабу нічого не доводить. Для приймання кандидата: повна еквівалентність normalized HTML та byte-identical embedded JSON/order на двох чужих уроках і 13 власних, негативні сценарії malformed/mutated roster/source, SHA/symlink, ID/UUID/type/locale/caller, неповні relation та snapshot; окремо переконатися, що курс і окремий test route не зачеплено. Якщо докази або точність вимірювання недостатні — нічого не доставляти.

**Методика майбутнього A/B.** Зафіксувати заздалегідь таймінг, primary statistic (paired difference на кожному уроці), шумову межу/мінімальний корисний ефект, баланс AB/BA в кожному блоці, однакові ізольовані guest sessions/workload, однаковий інтервал навіть коли swap відсутній, терміни stop/invalid та відсутність повтору до PASS. Перед зарахуванням пари перевіряти source digest **і** фактичну реалізацію: різний compile-time A/B tag на вході в конкретний змінений метод, одержаний лише в локальному захищеному мінімальному receipt разом з worker alias, тим самим способом і з тим самим накладним обліком для обох рук. Tag, зчитаний з іншого файла або диска, не доводить виконаний opcode; при невідповідності tag, повторному worker/cache transition, відсутності evidence чи timeout зберегти запис і зупинити/класифікувати блок за наперед визначеним правилом, не перезапускати кеш чи середовище. Якщо доказ можна отримати тільки в окремих debug GET, не заявляти, що виконуваний opcode перевірено в усіх timed GET. Порівнювати розподіл дельт за порядком/блоком з same-code baseline, не лише p95. На цьому етапі жодної зміни PHP/Apache/MySQL configuration не рекомендовано застосовувати.
