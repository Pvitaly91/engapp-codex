# PERF‑27 — HTTP-стиснення Gramlyze

База: [PERF‑26 `4d37552eb4994ba89a3c111969191c4d4270ce7b`](https://github.com/Pvitaly91/engapp-codex/commit/4d37552eb4994ba89a3c111969191c4d4270ce7b). Робоча гілка: `codex/perf-27-http-compression`. Дослідження лише в `gramlyze.loc` і локальних стендах; робочі дані, особистий прогрес, PHP застосунку, контент, `.ub`, production та `main` поза змінами.

## Вихідна конфігурація

XAMPP Apache 2.4.58 Win64, MPM winnt. `httpd -S` показує HTTP `:80` і HTTPS `:443` для `gramlyze.loc`, обидва з `D:/DEV/htdocs/gramlyze.loc/public`. Обидві секції підключають `gramlyze-fastcgi.conf`, який задає `mod_fcgid` з окремим PHP 8.5.10 NTS для Gramlyze (глобальний `php_module` завантажено, але цей vhost обслуговує FastCGI). `mod_proxy` і AJP завантажені; `mod_proxy_http` не завантажено, а для цього сайту немає `ProxyPass` або rewrite-передачі до проксі. Вихідні HTTP-запити йшли безпосередньо до локального listener з `Host: gramlyze.loc`, без клієнтського проксі, через HTTP/1.1. `mod_http2` вимкнено в конфігурації; HTTPS-заміри не підмінено HTTP-вимірами.

`httpd -M` не містить `deflate_module`, `brotli_module` чи `filter_module`, хоча відповідні DLL на місці. У PHP для Gramlyze `zlib.output_compression = Off`; served `.htaccess` містить лише наявні правила маршрутизації. ## Безпека: що не стискаємо

Спільний Blade layout каталогів, тестів і теорії вже містить `csrf_token()`. У режимах тестів HTML/вбудований JSON можуть містити CSRF, snapshot стану, підказки та інші сесійні поля. Запит без вхідного Cookie теж може створити сесію й отримати токен. Тому анонімний User-Agent, GET або відсутній Cookie **не** є дозволом стискати ці HTML-відповіді. Маршрути прогресу, адміністративні сторінки, сторінки помилок, upload/storage та runtime HTML не додаються до фільтра.

`/api/word-search/{uk,en,pl}` повертає обмежений набір публічних полів словника, а не значення запиту, і не запускає звичайну web-сесію. `/sitemap.xml` формує URLs зі спільного налаштування й публічного контенту, але проходить web middleware. Початковий придатний scope обираємо за позитивним доказом точного типу і розміру відповіді, а не через глобальний `AddOutputFilterByType text/html`. Не вмикаємо примусову компресію й не змінюємо Cache-Control.

## Кандидат gzip і HTTP-контракт

`gramlyze-apache-gzip.conf` (`2d46baffdc7d2c4299825f25cecae6c3ff0667398e5cfe954c45b50d2b03774a`) — рівень 6 для конкретних статичних URL, Apache handler і MIME яких доведено. Матеріал має бути реальним файлом, із числовим початковим `Content-Length ≥ 1024`, без `Range`, `Set-Cookie`, `Content-Encoding` та `private/no-store/no-transform`. Стиснені assets, будь-які динамічні відповіді й помилки поза дозволеним набором. Проксі, TTL, Laravel і маршрути не змінюються.

На приватному Apache 2.4.58: **30 HTTP-перевірок, exit 0**, `Syntax OK`. Приклад CSS **2400 → 61 Б**, decoded SHA точний. Спостерігали identity без `Accept-Encoding`, для `identity`, непідтримуваного алгоритму й `gzip;q=0`; 1023 Б без gzip, 1024 Б з gzip; pre-encoded reply не перестискається, а Range — `206 identity`. HEAD має 0 переданих байтів і перевірений `Content-Length` стисненої репрезентації для fixture. Vary існує на обох репрезентаціях та 304. Identity ETag дає 304; gzip з умовним Last-Modified дає 304 без тіла (Apache на ньому лишає identity ETag і без Content-Encoding); запит із gzip-ETag повертає повний **200 gzip**. Це обмеження revalidation Apache з окремими сильними ETag, не zero-byte gzip-304. Перші спроби закінчилися identity через фактичне ім’я статичного handler; виправлену умову перевірено окремим запуском.

Калібрування порога на реальних файлах, **offline, не HTTP**: `robots.txt` 71→87 Б (розширився), `favicon.svg` 622→339 Б та маленький JS 737→403 Б (економія до 0,35 KiB), фон 1129→567 Б, JS прогресу 1318→458 Б, SVG 2261→823 Б. Поріг 1024 Б навмисно лишає малі виграші за межами та уникає розширення найменших відповідей; фактичний wire виграш перевіряється окремо.

## Контрольований приватний стенд

Той самий Apache 2.4.58 виконує реальне HTTP-стиснення на двох дозволених loopback-портах. A/A — один і той самий режим без фільтра; A/B — однакові frontend-налаштування, точні статичні байти served ROOT та той самий код PERF‑26, різниця лише в локальному include B. Для динамічних відповідей стенд передає обом рукам однаковий PHP CLI handler. Це **не** live FastCGI; absolute TTFB різних SAPI не порівнюємо. Backend обмежено шляхом, nonce і приватною session cookie (та штатними `locale`/`XSRF-TOKEN`), MariaDB працює в read-only транзакції з allowlist запитів на читання; POST progress дозволено лише прогону паритету у приватному file-session контурі. Немає записів у робочу БД.

Таймінги не використовують примусове RNG-симулювання; повний HTML, JSON і відновлення перевіряються окремим seeded запуском. Однакова підготовка й ротація порядку маршрутів, ABBA/BAAB, виключені primer, медіана та nearest-rank p95/p99. Усередині таймінгу час PHP та його CPU/allocator — окремі від Apache process CPU/RSS; у клієнті тіло читається повністю та вже після встановленого last-byte перевіряється декомпресією/SHA. Статичні файли віддає Apache напряму, без PHP.

Збережені спроби паритету: `parity01` спинилася до HTTP через помилку транскрипції приватного контрольного піна; `parity02` не пройшла надто вузький whitelist тестової cookie мови. У `parity03` пройшли 76 HTTP, 33 пари, обидва progress store/resume/reset, JSON, порядок UUID, локалі й assets; 20 пар мали відмінний **лише повний HTML hash**. Причину локалізовано у spelling приватних портів всередині URL-encoded та JSON-escaped абсолютних URL. `perf27-html-dia02` після вузької нормалізації саме відомого приватного origin у трьох формах, приватних CSRF/Livewire частин — 8179 рядків з кожного боку, 0 відмінностей на Past Perfect. Це не підміняє повторний широкий паритет.

`perf27-private-parity04`: 38 HTTP, **17/19** точних fresh пар після першого уточнення нормалізації. У двох theory було по одному відмінному рядку — той самий номер приватного порту в Alpine `JSON.parse` URL словника, але з потрійним екрануванням. `perf27-theory-dia02` повторив **лише ці дві пари** й нормалізував тільки точний origin також у цьому написанні. Повний HTML збігся: Passive 7132 рядки/595 003 символи, Word Order theory 7160/596 544; нуль відмінних рядків. Підсумкове покриття **19/19 fresh** після окремого підтвердження двох пар; не переписуємо попередні неуспішні результати. UUID, порядок, вбудовані питання з відповідями/підказками, локалі, JSON словника та private store/resume/reset у двох руках були еквівалентні окремо.

## Активація та відкат

**На активному `gramlyze.loc` стиснення не застосовано.** На наявному XAMPP відсутні завантажені `mod_deflate` і `mod_filter`. `LoadModule` — директива головної конфігурації Apache, її не можна застосувати тільки всередині Gramlyze vhost; DLL на диску не змінює цього. Умови задачі виключають зміну спільної конфігурації Apache, тому не було заміни конфігурації, graceful reload або тестів «після застосування». Усі п'ять початкових SHA конфігурацій і активний PHP engine PERF‑26 (`a88cdf061fa79279fb378c8f2765a6866fa40513abae8ef9646e8701d2833e53`) збіглися під час повторної перевірки. Доказ живого HTTP — вихідний identity; позитивний gzip доведено лише через приватний Apache на loopback.

[Посібник застосування і точного відкоту](../operations/perf-27-http-compression.md) описує preimage + SHA, `httpd -t`, підтримуваний graceful reload, повтор HTTP/Chromium/API та перевірку сторонніх vhost **після окремо дозволеної активації**. У PERF‑27 відкат живого сайту не потрібний: ми не змінювали його конфігурацію. Для Nginx є лише версіонований приклад для вузької майбутньої allowlist; Nginx у цій роботі не запускався, `.ub` та production не змінювались.
