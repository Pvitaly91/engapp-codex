# PERF‑26 — пам’ять Native Content Engine

База: [PERF‑25 A2 `0d6fcf29b15c8b338cfdcea27b92b089cff8a287`](https://github.com/Pvitaly91/engapp-codex/commit/0d6fcf29b15c8b338cfdcea27b92b089cff8a287). Гілка: [`codex/perf-26-native-content-memory`](https://github.com/Pvitaly91/engapp-codex/tree/codex/perf-26-native-content-memory). `gramlyze.loc` — єдине середовище. Не змінюємо навчальні дані, робочу БД, особистий прогрес, `main`, `.ub` або production. Відхилений диспетчер PERF‑25 B не повертається.

## Від чого відштовхуємося

[Звіт PERF‑25](perf-25-centralized-native-content.md) зафіксував +8 MiB виділеної PHP allocator пам’яті на UK Present Simple Passive theory та +6 MiB на першому PL To Be Compose, водночас зі значним скороченням TTFB та CPU. Це не вимір активної пам’яті і не вимір RSS. Точний початковий engine на served ROOT — `c03d1c7e009a2fc1b229ea44d57cafcedfbd44a6ca17d4e6f5031449db2ac361`, менеджер — `042be99b914e6705f30af5ef5b7b5bf6c79259ba841dbcd2f7dbfd1e9364df2c`.

Кеш PERF‑25 створює окремий запис на профіль та caller тільки в межах точного Request. Повний `profile` включає версію, owner bindings та піновані артефакти; ці поля потрібні для strict comparison. Верхні PHP-масиви можуть розділяти дочірні структури за COW, тож розмір файлів і кількість присвоєнь не доводять фактичне дублювання. Допоміжні артефакти, відмінні від BEFORE/PATCH/MASTER, після холодної валідації не зберігаються в записі.

Дві перевірні гіпотези: (1) renderer `pointPanels`/`correction` після позитивного `validDesign` повторно викликає `load()` та одночасно утримує вже закешоване і щойно декодоване дерево; (2) standalone результат відновлення не використовує MASTER після валідації, а theory не використовує BEFORE. У Compose один запит може утримувати дерево більше ніж одного пакета; замірюється обсяг та кількість. Не вводимо політику витіснення за умовною кількістю записів без окремого доказу декодувань, пам’яті й TTFB.

## Незалежні точні кандидати

- **R — theory panels/corrections.** Повертає дерево, яке щойно пройшло точну `validDesign`-перевірку; перед тим як використати його замість другого `load()`, **ще раз** перевіряє всі піновані байти в тому самому порядку. Якщо другий етап бачить помилку, вона так само виходить із helper, як помилка другого `load()` на базі. Нового cache scope немає. Лише engine `b762fa68e59d3d123e5b46ead2dda98517d6a636126e0d238c142cf51f2bed46` (`panels-reuse`).
- **C — короткий source tree за caller.** Повне холодне завантаження й валідація залишаються. Для standalone retained дерево вже не утримує MASTER, бо цей caller читає лише точний AFTER-блок і BEFORE. Для theory не утримує BEFORE. Binding перевіряє UUID, owner, page/category, locale, metadata і точні bytes BODY як раніше; MASTER продовжує забезпечувати `lesson` при presentation. Старий course шлях не змінено. Лише engine `a88cdf061fa79279fb378c8f2765a6866fa40513abae8ef9646e8701d2833e53` (`retained-projection`).

Обидва snapshots спираються на незмінний PERF‑25 A2, вимірюються окремо й не застосовуються до локального runtime до приймання. Для пам’яті розрізняємо `memory_get_peak_usage(false)` (активні PHP алокації) та `memory_get_peak_usage(true)` (виділений allocator); RSS, якщо доступний, не прирівнюється до жодної PHP-метрики. Для latency зберігаємо paired directions та p95/p99, а не лише зміну медіани. Новий гість не означає холодну базу.

## Фактичні алокації A2: діагностика окремо від latency

`perf26-mem-a2-base01`: 30 GET у приватному інструментованому процесі з точним baseline. Passive theory: максимум **14 фактично живих source entries** (M56, M53–55, M57–59, M77/78/80/81, M65–67). Ексклюзивне очищення самих source arrays після `terminate` звільнило **9 746 448 Б** (~9,29 MiB) активної пам’яті; metadata та Request/Route references — ще **10 672 Б**. Звільнення PHP об’єктів не повернуло allocator pages в цій точці. PL та EN To Be Compose: **два** одночасні дерева (M85 + M71), ексклюзивно **2 050 112 Б** разом, metadata **1648 Б**. Це вимір реальної алокації після звільнення, не оцінка за JSON file size. Якщо arrays також читають інші живі споживачі, reclaim показує лише ексклюзивну частину.

На theory є ще один життєвий цикл: `PassiveVoicePracticeSupplement::compile()` після власного `load+validate` утримує повні tuples у локальному `$releases`, хоча далі читає лише PATCH targets. Його presentation може одночасно наповнювати Request-джерела. Аналогічний локальний lifetime у Basic Grammar й інших supplement компіляторах. Сам renderer також виконує додаткові `load()` для панелей і виправлень. Тому ні пік під Blade, ні розрив allocated/active не пояснюються лише метаданими мемо. У прибраних профілем фактичних структурах не було підстав змінювати identity-зіставлення або вводити числовий ліміт кількості пакетів тільки за припущенням.

**Де саме пік.** Passive theory `r00002`: на вході в root Blade 6 207 680 Б active, останній проміжний high-water 48 548 008 Б (memo hit/bind M67), на виході 48 424 936 Б, найвищий peak під Blade **49 267 168 Б** із 14 живими записами. Це накладання кількох життєвих циклів після холодної валідації одного джерела. PL Compose `r00005`: dataset стартує на 4 441 048 Б, після ORM завантаження 9 481 712 Б, після повних M85/M71 decode та validate 10 840 832 / 11 805 192 Б. Внутрішній `definition` працює з тимчасовими COW-проєкціями, наприклад перша M71 11 801 072 → 11 853 312 Б; це не окрема друга копія всього профілю. Peak **12 782 880 Б** уже до завершення dataset під час memo hit/binding, потім dataset повертається до 7 541 864 Б active, а Blade закінчує на 10 475 848 Б. Отже звільнення всього standalone cache після dataset саме по собі не зменшило б наявний active high-water у Compose.

На PL Compose три послідовні інструментовані GET дали 46/32/26 MiB allocated при стабільній active роботі після прогріву. Це узгоджується з ефектом allocator arena між запитами, а не з рівним приростом живих дерев. Для RSS `getrusage()['ru_maxrss']` у приватного процесу 133152 KiB збігся з Windows `PeakWorkingSet64` 136 347 648 Б; snapshot `WorkingSet64` у спокої 103 034 880 Б. Обидва виміри RSS стосуються процесу, а не лише PHP-структур конкретного запиту; lifetime max не є одночасним піком групи процесів.

## Непрофільований A/B незалежних R та C

`perf26-tri01`: 150 HTTP і 80 парних порівнянь (40 на кандидат); P — точна A2 база, S — лише R, D — лише C. Спільний P вимір спарено окремо з S і D, код кандидатів не змішано. Порядки P/S/D → D/S/P → S/D/P → P/D/S розгортаються в ABBA/BAAB для кожної проєкції. Вісім штатних native PL Compose shuffle відмінностей, seeded раніше точний. У колонці Start active/alloc — поточні байти перед скиданням peak; це дозволяє відрізнити спадок allocator від нових алокацій.

**R:** active й allocated peak ті самі (до 0,1 MiB) на всіх десяти маршрутах. Теорія Passive дала −3,51% TTFB медіани, але потрібний кандидат на пам’ять не доведений. **C:** стабільне зменшення active на приблизно 0,3–1,36 MiB (PL Compose 12,07 → 10,71, Passive theory 46,24 → 45,06, Word Order theory 40,26 → 39,49 MiB). Виділені 42 MiB на Compose вже на вході в kernel у кожній руці й не зростають за запит; їх не можна інтерпретувати як live allocation Compose. На кількох тестах зменшився сам стартовий allocator floor, тому не зараховуємо цю дельту як доведений per-request peak. У Present Simple і PL Past Passive у цій серії є сигнали latency, у т.ч. в обох порядках; R, який не змінює цей шлях на card, також розійшовся з P. Потрібен незалежний контроль перед будь-яким застосуванням C.

## Відбір і приймання

- **R — не приймати:** менше повторних декодувань не знизило пік. **Q — не приймати:** менше тимчасових структур у компіляторі не досягає пізнього піку сторінки. Обидва лишилися окремими приватними експериментами.
- **C — доведений частковий виграш:** 0,3–1,36 MiB активного піку на запит у широкій серії, повторено на контрольних маршрутах та з трьома гостями. На двох Compose під паралельним навантаженням медіанний пік allocator знизився на 2 MiB на гостя, а максимуми ні. Додаткові історичні **6–8 MiB не усунено повністю**; зниження RSS не доведене. Контрольні виміри не підтвердили початкового великого сповільнення; залишаються малий серійний сигнал Present Simple та описаний вище ризик CPU/медіани під паралельним Compose. Ухвалення вузької проєкції засноване на повтореному memory виграші, збереженій функціональності й відсутності відтвореної істотної втрати TTFB, а не на твердженні про повну рекуперацію 6–8 MiB.
- `perf26-browser-c01` — точний C з приватного overlay, Chromium 147: **5/5 HTTP 200**, Card UK/EN, Step UK, native theory UK, PL Compose, без JS-помилок. На UK Card — помилкова та правильна відповідь без подвійного бала, reload із серверним відновленням приватної спроби, restart і реальний autocomplete. Theory показала вбудовану практику; Compose — теоретичну панель і вибір токенів. Сім POST обробив лише приватний file-session стенд, два змодельовано без запису в сайт.
- Фінальна перевірка точного C після прибирання Q: **25/25 PHP, 854 твердження, exit 0**, один успадкований deprecation. Додаткові твердження перевіряють, що обидва standalone memo не тримають MASTER, а theory memo не тримає BEFORE. Попередня спроба у restricted контексті не відкрила PHPUnit bootstrap (exit 2); запуск через весь каталог із `--filter` виконав ті самі 25 тестів без assertion failures, але виявив 60 сторонніх порожніх класів (exit 1). Успіх зараховано лише для окремого повтору з трьома явними тестовими файлами.
