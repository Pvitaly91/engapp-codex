## Резервування і межі

Перед змінами у release виконано точне резервування `.env`, сайту Nginx і поточних налаштувань PHP-FPM у приватний каталог 0700; `.env`/APP_KEY лише в захищеному файлі, його значення не виводилися. Верифіковано побайтовий збіг `.env` та конфігурації vhost; збережено SHA чинного Nginx і сусідніх vhost, фізичні шляхи та права, inode сесій/uploads, інвентар збереженого меню. Робоча схема MySQL зафіксована read-only транзакцією: 46 таблиць, 82 записи міграцій, остання batch 41. Рядки змісту та сесії в SQL backup не експортовано; дамп не імпортувався. Чинні файли та DB не перезаписувалися під час створення candidate.

Перша пробна передача Git archive виявила дію Windows `core.autocrlf=true`: історичний frozen JSON не пройшов байтовий SHA guard, тому цей кандидат не запускався. Окремий експорт із вимкненою конверсією звірено з точними Git blobs, хибну копію відокремлено без змін live. Вимірювання проводяться лише на Ubuntu.

## Linux immutable delivery

`immutable-linux.cjs` повторно використовує PERF-29 builder і перевіряє фізичний POSIX vault, publisher/worker і всі батьківські каталоги. Довірений `vitaly` публікує нові покоління без перезапису. Serving tree має readonly CSS/JS і gzip, приватні метадані залишаються недоступними worker/HTTP. Root master перевірено за inode фактичного бінарника Nginx. Негативний credential probe на Ubuntu: **16/16** на disposable fixtures, із фактичними UID/GIDs worker та очищеними capabilities; SHA тестових immutable файлів не змінився. Прочитання дозволених файлів працює, write/append/delete/rename/replacement/timestamp/chmod/chown і link не дозволені.

Збережено старе покоління `f852c6d84ec4c9ceadaed1405c32988746cbbe812bebbb829ff2e9784398deb0` і нове `17c5bd9a25b1196297362b43fad894a68d3f557935d398376c8b0f91180df989`. Нові URL не потрібні. SHA перевіреного include `894c2e6c5033727b54543867ed2d5b95f8a6cf9d548bddb1dd42f242216d7766`. Відповіді C мають нативний [gzip_static on](https://nginx.org/en/docs/http/ngx_http_gzip_static_module.html) тільки в exact Vite locations, окремі strong ETag для відповідних представлень, однаковий Last-Modified і `Vary: Accept-Encoding`. Немає саморобного Content-Encoding чи `gzip_static always`. Guard блокує sidecar, metadata, sourcemaps, невідомі fingerprinted шляхи; immutable TTL тільки для прикритих запечатаних файлів.

**59/59 HTTP-контрактів на нативному Nginx C**: фактичний raw/decompressed SHA, 200/HEAD/304/206, identity, gzip;q=0, MIME, Vary, ETag, Last-Modified, 404, відсутність подвійного gzip і публічного доступу до метаданих. Перший launch helper відхилив uid 0 як чужого publisher ще до запису; після передачі публікації законному власнику перевірка пройшла. Немає зміни чинного Nginx/FPM.

## Активація, rollback та відкритий крок

- **Gzip: PASS у shadow; не активовано на live. PHP: BLOCKED для активації.** У зіставному Ubuntu A/B/C перше відкриття Past Perfect Forms має відтворюваний приріст TTFB близько **46%** після заміни PHP, і з gzip, і без нього. Вимірювання виконано на окремих FPM pools, з ізольованими сесіями й відмінним від live профілем кешу; це не виміряна live-регресія. Невирішений браузерний сценарій — додаткова причина не активувати release.
- Чинний vhost, PHP-FPM pool, БД, uploads та особистий прогрес не замінювалися. Останній перевірений live root — `/var/www/gramlyze.ub-e7b4c0/public`. Немає нового активного SHA, результату після активації або rollback: перемикання не виконувалося. Є лише локальні зміни інструментів та EOL-атрибутів, приватна збірка, верифіковані static generations і приватні конфіги стенда. Windows `hosts` — окрема погоджена зміна одного запису на `.103`.
- Процедура для окремо прийнятої майбутньої активації: перед перемиканням повторно звірити preimage чинного `.ub` vhost, inode і шляхи, окремо перевірити відсутність конфліктів у shared FPM/cache та сумісність існуючих сесій/uploads. Зберегти точний preimage і обидва незмінні покоління; перевірити повний ефективний конфіг через `nginx -t`. Атомарно замінити лише файл/вказівник `gramlyze.ub` і виконати graceful reload. Перевірити live HTTPS, фактичний PHP release, gzip/identity та повторити заміри. При критичному FAIL відновити точний попередній vhost/вказівник на попередній root, знову `nginx -t` і graceful reload; не відновлювати БД, не очищати спільні сесії/кеш і не перезапускати сусідні служби. Якщо потрібно працювати з OPcache, використовувати окремо підтверджений FPM pool, а не вважати Nginx reload його очищенням. Ці кроки не запускалися на live.
- Наприкінці встановлене SSH-з’єднання закрилося, нове суворе підключення до `192.168.0.103:22` завершилося `Connection timed out` ще до входу. Не підключалися до іншої адреси. **Очищення не підтверджено:** після відновлення SSH треба зняти саме `gramlyze-perf31-chromium-tHKteisl` з наданого приватного профілю і перевірити його відсутність; завершити тільки приватні Nginx/FPM за перевіреними PID та перевірити порти 18081–18083. Повторно активувати профіль, змінювати IP навмання або перезапускати чинні служби не потрібно.
