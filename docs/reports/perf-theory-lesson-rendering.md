## Свіжий профіль і причина

Окремо від неінструментованого baseline виконано по одному гостьовому warm-up і одному профільованому warm-запиту на Word Order, Past Perfect Continuous (PPC) та M94. Усі три відповіді — HTTP 200, UK, development, HTML без стиснення. Зонд працював лише для зазначених локальних GET із приватним ключем і не повертав діагностику в HTTP. Web/CLI identity порівнювалася за HMAC фізичного кореня застосунку та налаштованого підключення; SQL bindings, cookies, відповіді та ідентифікатори сесії не записувалися.

Початковий probe із серії `before-id` помилково обгортав не тільки controller view, а й уже відрендерені рядки внутрішніх view. Через це в ньому було кілька вкладених `blade.document`; він збережений як діагностична спроба, але не використаний для висновків про HTML чи агрегованого часу Blade. Нижче — виправлена серія `before-widgets`: тільки повернення view контролера обгорнуто, по одному `blade.document` на запит. Після неї 35 змінених для профілювання шляхів повернуто до зафіксованого стану, включно з видаленням двох тимчасових runtime-файлів.

Лічильники builtins охоплюють лише інструментовані файли. `definition` вкладений у `validate`, а читання, хешування й JSON — зокрема у `load` та `definition`; inclusive-суми цих рядків не додаються. Незалежна сума self тільки для `load` + `validate` — 333.36 / 259.25 / 148.41 ms, без `definition` та інших інструментованих дочірніх операцій.

**Підтверджена причина.** Спільний Blade практики перебирає компактні проєкції. Базовий `TheoryPracticeCompactProjection::presentation()` викликає `load()`, який під час першого доступу декодує і повністю перевіряє документ, ще **до** зіставлення binding поточного блока. Для звичайного PPC немає прийнятого package presenter, але компактні презентації витрачають близько 2.42 с. Найдорожчі окремі проєкції у Word Order / PPC: Conditionals — 277.77 / 256.95 ms; Pronouns/Demonstratives — 252.11 / 278.57 ms; Passive Voice — 223.53 / 216.10 ms; Questions/Negations — 209.48 / 220.36 ms. Це не вартість короткого порівняння власника: вона припадає на вкладені перевірки чужих артефактів.

Конкретні ребра у Word Order і PPC підтверджують джерело: `renderer → PrepositionsPhrasalPracticeCompact::presentation → load → validate`; далі `PrepositionsPhrasalPracticeSupplement::load → PrepositionsPhrasalPracticeSource::load → deriveTargets`. Останній складає контрольні native blocks і викликає `M77.binding` п’ять разів і `M78.binding` двічі, хоча поточний урок не їхній. `BasicGrammarPracticeCompact::validate` запускає п’ять `M83.binding`, `MixedRevisionPracticeCompact::validate` — ще один. На PPC сам `TheoryContentSource` лише відхиляє чужі presenter-и; ці дорогі перевірки їхніх синтетичних блоків приходять з іншої гілки. При повторному вході віджетів частина джерел уже підготовлена цією роботою, тому їхні warm spans не можна трактувати як незалежну вартість повного першого завантаження.

**Чому не інші кандидати.** M42 уже має три `sourceSignature` на кожному уроці (19.19–24.61 ms); меню читається за 0.73–1.71 ms. SQL, topic cards і добір практики не домінують. Прямий memo release міг би скоротити частину повторів, але залишив би перше повне завантаження сторонніх compact-документів; після встановлення їхнього call-site ціль вужча. Не виявлено повторів одного render phase: у Word Order — 0 пар, PPC — 3 base/detail, M94 — 1 base/detail з різними входами. Вартість окремих detail-проходів — 12.87 ms сумарно на PPC і 30.23 ms на M94; validation render не вилучався. M94 також показує значні незалежні витрати widget hints, але на двох основних уроках більший і спільний внесок має саме compact dispatch. На цьому етапі обрано лише його, без паралельної зміни widget projection, selection, M42 чи верстки.

Ці точкові заміри пояснюють механізм, але не є оцінкою медіани, p95 або доказом парного прискорення. Файлові хеші залишилися близькими за кількістю: рання маршрутизація **після** перевірки frozen SHA, а не замість неї. Пам’ять PHP в цих спостереженнях нижча; про RSS і довгі процеси висновку немає.

У B ланцюг до `PrepositionsPhrasalPracticeSource::deriveTargets` і далі до M77/M78 ще є, але не під compact-викликом. Тому не заявляємо, що зникли всі перевірки сторонніх джерел; зменшився сумарний час двох неперекривних гілок. Окрема оптимізація widget projection не входила у B.

Після цього follow-up усі 35 шляхів перевірено за manifest точних preimages B; відмінностей немає, тимчасові probe і control відсутні. Приватні лічильники лишаються поза Git; наведені числа не підміняють фінальний HTTP/browser smoke.

## Парні вимірювання уроків без діагностики

A — перевірений served стан після PERF-01/02/03; B — лише кандидат із ранньою перевіркою власника в `TheoryPracticeCompactProjection.php`. Послідовність ABBA формує сусідні пари AB/BA. На кожній фактичній заміні байтів коду в будь-який бік, а також перед першим запитом витримано однакові 2200 ms поза заміром. SHA-256 кандидата й решти контрольованих файлів перевірявся до/після запитів. Гостьові UK HTML GET ідуть через нове TCP-з'єднання; для warm-up і всіх warm-пар однієї цілі — спільний тимчасовий cookie jar, без очищення серверних кешів. Профайлер вимкнено. Після серії відновлено A.

До старту зафіксовано timeout 60 с і критерії відсіву: транспорт, не-200, невірний тип відповіді/мова/режим/кодування, відсутній очікуваний набір або меню, profiling header чи зміна контрольованого коду. Валідна розбіжність HTML не була б критерієм відсіву. У серії уроків **жодного виключення, таймауту або повторного запиту**. ## Прийнята зміна

Єдина зміна runtime — `app/Support/TheoryPracticeCompactProjection.php`. Після перевірки джерела та декодування маніфесту проєкція не запускає повну валідацію для секції з явно іншим власником, якщо всі bindings однозначно задають власника. Збіг, відсутній власник або невизначені дані залишаються на попередньому шляху валідації. SHA-256, перевірка файлу та симлінків, прив'язки до блока, його даних і груп не послаблені; нового кешу немає. Публічне `load()` і caller межі збережено. Другу оптимізацію не додано: після виключення зайвих валідацій частина роботи перемістилася до віджетів, але незалежні HTTP-пари вже підтвердили виграш однієї зміни.

Фінальний SHA-256 runtime-файлу в WT і served ROOT: `e755708c45595e51a791d2fc4e6c804e42087121bc32b496285336b4d2d326a2`. Тест нового guard — `tests/Unit/TheoryPracticeCompactOwnerGateTest.php`. Звіт — `docs/reports/perf-theory-lesson-rendering.md`. Це повний список файлів PERF-04 для наступного checkpoint.

## Автоматичні перевірки

Робочий `.env` не завантажувався. Windows checkout початково видав CRLF у частині hash-bound fixtures.
