# PERF-29 — Immutable Static Assets Delivery

Локальна перевірка Gramlyze на Windows/XAMPP, лише `gramlyze.loc`. База — `54b4872999bb4ed00f79ca9421f1eb0b0f59e405` (`codex/perf-28-precompressed-static-assets`). Гілка результату — `codex/perf-29-immutable-static-delivery`.

**Рішення: PARTIAL_PASS, не активовано.** Ізольований D зберіг економію трафіку й відновив пропускну здатність. Підвищені права чинного Apache не дають перенести доказ незмінності на live vhost без зміни способу запуску спільного сервера.

## Модель публікації

1. Збірник зчитує фактичний Vite manifest і дозволений граф CSS/JS. Незмінний інвентар містить копію Vite manifest, публічний URL, MIME, timestamp, довжину й SHA-256 обох представлень. Кожен gzip розпаковується й звіряється з identity, а нестискуваний або невигідний файл зберігається тільки як identity. Пошкоджені файли, непередбачені файли, hardlink і reparse point відхиляються.
2. Повністю перевірені файли отримують content-addressed ім’я на тому самому томі. Це ще **не** HTTP-публікація: vault поза document root, і немає активного Apache mapping. Ніякого перезапису покоління або автоматичного видалення старого. Повторне використання fingerprint із чужими байтами відхиляється.
3. До публікації NTFS-валідація перевіряє фізичний шлях, права батьківського каталогу, vault та всього дерева. Процес HTTP має читати, але не записувати дані, додавати/видаляти файли, змінювати timestamp, DACL або власника. `OWNER RIGHTS` не дає власнику неявно повернути `WRITE_DAC`; довірені SYSTEM/Administrators лишаються поза цією межею. Звичайного атрибута read-only недостатньо.
4. Renderer перевіряє NTFS до та після читання маніфесту. Один згенерований include задає обидва варіанти й перелік збережених поколінь. Після `httpd -t` встановлення цілого перевіреного include (не дописування частин) та штатне перечитування конфігурації є точкою активації; попередня конфігурація лишається придатною до відкату, а старі bytes — доступними старим процесам. Немає request-time хешування чи перечитування живого оригіналу на замапленому URL. Якщо запечатування або окремий доступ до live-процесів не доведені, старий механізм не замінюється.

Немає змін Vite, Blade, PHP, клієнтських скриптів чи URL. Зокрема, `english-answer-variants.js` і `theory-search.js` мають поточний Blade URL із `filemtime` у query, а SVG фонів посилаються зі сталих URL. Це не незмінні Vite-імена, тому реальний пакет D їх не перенаправляє. Окремий закритий статичний стенд запечатує обидва SVG лише для однакового шестикомпонентного порівняння з PERF-28. Випускати fingerprinted aliases для stable assets без міграції всіх викликачів і доказу сумісності не запропоновано.

Джерела контракту: [права NTFS](https://learn.microsoft.com/en-us/windows/win32/wmisdk/file-and-directory-access-rights-constants), [OWNER RIGHTS у Windows](https://learn.microsoft.com/en-us/windows-server/identity/ad-ds/manage/understand-security-identifiers), [нативні валідатори Apache 2.4](https://httpd.apache.org/docs/2.4/mod/core.html#fileetag).

## Методика

- A — identity; B — початковий Apache gzip PERF-27; C — точний PERF-28 із перевіркою оригіналу при запиті; D — перевірений immutable include. Окремі loopback vhost, однаковий `httpd.exe` SHA-256 `7bd994ae100f079c7c2e36414ec40c059b38d440f0c48e89c0946896c8b0aeea` (2.4.58 Win64), модулі й вхідні payloads. A/B/C/D: рівні [1, 3, 5, 10, 20], по 24 хвилі на варіант/рівень/серію; збалансований Williams-порядок і зворотний фізичний порядок запуску в другій серії. Для кожної відповіді перевіряються статус, bytes та SHA декодованого вмісту; для C/D — також SHA закодованих bytes. Праймери не входять у заміри.
- Критерій до оцінки D: ~81% економії encoded body; медіанна пропускна здатність поблизу A — орієнтир не нижче 90% identity на 10 і 20 паралельних, у межах A/A шуму; дивитися також на CPU, latency хвостів і відсутність істотної сталої регресії на інших рівнях. Це локальний статичний тест, не прогноз абсолютного production throughput.
- TTFB — до заголовків, total — до повного тіла. Throughput — хвильові req/s. Wire — фактичні HTTP bytes із заголовками/framing, без TCP/IP overhead. CPU — дельта процесу Apache, RSS — peak за життя виміряного процесу. Windows process read I/O не гарантує обліку mmap і не є окремою трасою дискових файлових викликів.

## HTTP та регресії

- **45/45** контрольних HTTP-відповідей на точному XAMPP Apache, перевірка синтаксису й фактичного PID перед HTTP. Статуси 200×31, 206×3, 304×4, 404×3, 406×4. Перевірено нормальний і wildcard Accept-Encoding, явне `q=0`, пріоритет між явно заданими вагами, identity fallback і відмову, коли немає прийнятного представлення. MIME, Content-Encoding, Content-Length, Vary, HEAD, роздільні strong ETag та Last-Modified, умовні запити, If-Range, часткові identity/gzip bytes, відсутність подвійного gzip. Динамічні/приватні URL та сирі sidecar не входять у mapping. Історичний fingerprint доступний після видалення mutable оригіналу зі стенда, два однакових SHA з новим mtime не конфліктують, підміна bytes під тим самим fingerprint відхиляється. Receipt: `storage/logs/perf-29/immutable-http-t47nZ3/http-contract-ad3d6586-b727-41b2-9e80-e7e1e0011ee8.json`; include SHA `d81e786f2b03ee1fa050e44476f13792c54d4bfe89b3a1da85f705f93937785a`. - Node **126/126** зі збереженням перевірок попереднього збірника, відповідей, retry та класифікації стану. Початкова невдала спроба junction у обмеженому контексті — **EPERM**; штатний ізольований повтор із нормальними дозволами пройшов. ## Пакет та межа активації

Пакет складається з `tools/perf/http-compression/immutable-release.cjs`, `seal-release.ps1`, `immutable-delivery.cjs` та відповідних тестів. Точний Git SHA реалізації: `a9e747b15d26ceec340a8e2fbeed70e492e415c9`. Гілка: [codex/perf-29-immutable-static-delivery](https://github.com/Pvitaly91/engapp-codex/tree/codex/perf-29-immutable-static-delivery). Для повторення збору:

1. Видати новий, приватний і фізичний NTFS vault через `seal-release.ps1 -Mode Init -ReleaseRoot <новий C:\Gramlyze.PERF29.HEX>`. На тому самому томі: `immutable-release.cjs stage --public <public> --root <vault>`, потім `prepare --staging <generation> --sha256 <manifestSha256> --public <public> --root <vault>`. Для справжнього сайту не використовувати `--isolated-with-stable`.
2. `seal-release.ps1 -Mode Seal -ReleaseRoot <vault>`, повторно `-Mode Verify -ReleaseRoot <vault> -ApachePid <фактичний PID>` **для кожного процесу** цільового Apache; якщо PID, токен чи файлову межу не підтверджено, зупинитися. Для нового покоління підготувати новий vault, не переписувати попередній.
3. Для поточного покоління перевірити `assertFresh`, потім викликати `immutable-delivery.cjs::render({publicRoot, generations:[{generation,expectedDigest,sealRoot}, …], scope:'vite'})`. Починати з нового pin і включати потрібні старі. Перевірити SHA цілої конфігурації на диску, перевірити `httpd -t` включно з порядком розміщення перед fallback правилами конкретного vhost. Не додавати нових модулів або змінювати global конфігурацію. Після окремого дозволу на зміни при потребі: зберегти preimage власного include та SHA, замінити include атомарно на тому самому томі, перечитати його штатним способом.
