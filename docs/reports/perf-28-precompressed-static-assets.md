# PERF‑28 — попередньо стиснена статика Gramlyze

База: [PERF‑27 `b16f622da4e33c37405247830782aa2b5934a582`](https://github.com/Pvitaly91/engapp-codex/commit/b16f622da4e33c37405247830782aa2b5934a582). Гілка: `codex/perf-28-precompressed-static-assets`. Середовище: `gramlyze.loc`. Динамічний HTML, Laravel, навчальні алгоритми, робоча БД, особистий прогрес, `.ub`, production і `main` не входять до змін.

## База і можливості Apache

[PERF‑27](perf-27-http-compression.md) підтвердив приблизно 81% економії реальних HTTP body bytes та ідентичний decoded SHA, але при 10 паралельних статичних запитах зафіксував **772,18 → 647,19 req/s** (без фільтра → динамічний gzip). Це історичні дані, не baseline поточного запуску. На активному `gramlyze.loc` PERF‑27 не вмикав gzip.

Поточний XAMPP Apache **2.4.58 Win64 (mpm_winnt)**: `rewrite_module`, `headers_module`, `mime_module`, `alias_module` і `authz_core_module` є в `httpd -M`; `deflate_module` і `filter_module` не завантажені. Конфігурація `:80` і `:443` підключає власний `gramlyze-fastcgi.conf` тільки для Gramlyze. Живий запит до CSS з `Accept-Encoding: gzip` відповів HTTP/1.1 200 та 123 022 Б (identity). `mod_fcgid` і код PHP лишаються на тому самому шляху для динаміки.

## Збірка й контракт C

`precompress.cjs` — окремий крок після звичайного Vite build. Проходить лише підтверджені Vite entry points і їхні CSS/JS залежності, явно дозволені `public/js` та SVG. Оригінальні paths/hash і Vite manifest незмінні. Gzip level 6, фіксовані заголовки без часу збірки; окремий файловий Last-Modified sidecar відповідає джерелу до секунди. Мінімум **1024 Б джерела** та збереження **≥256 Б і ≥10%**: дуже маленький `robots.txt` у PERF‑27 міг збільшуватись (71→87 Б), а економити коротких документів/ресурсів за будь-яку ціну немає сенсу. На актуальному manifest перевірено **21** файл, **15** мають gzip, **414 831 → 85 881 Б** серед придатних. Inventory SHA‑256 `3edaf3bc7ec9ff750160439a8419fe001f98d9071ac0f7e849eefced61557ba8`. Це байти збірки, не вимір мережевого трафіку.

Рендерер генерує місцевий **vhost-only include** тільки після незалежної повторної перевірки SHA‑256 декодованого оригіналу й точного gzip. Архіви поза public root; немає загального Alias, прямий URI `.gz` не дозволяється, відсутня статика не проходить у Laravel. На кожному придатному gzip-запиті Apache перевіряє вихідний текст (SHA‑1 через `ap_expr` як runtime-індикатор зміни, не заміна SHA‑256 при публікації), розміри оригіналу й sidecar та відсутність symlink. Зміна джерела з тим самим розміром і Last-Modified переводить запит на identity. Відсутній або обрізаний sidecar теж дає identity. Довільне пошкодження бінарного файла того самого розміру відсіює активаційне `verify`; загальне припущення після публікації — приватне незмінне покоління поза робочими uploads і Vite.

- **Node builder 8/8 PASS.** Два build дали точні байти, перевірено scope/поріг, старий і новий manifest, відсутні/зайві/пошкоджені gzip, застарілий оригінал, символічні посилання, NUL, UTF‑8 та CLI. Перша managed-спроба показала незаповнене Windows device поле та недоступність junction; підтверджений остаточний test run пройшов у дозволеному контексті.
- **HTTP-контракт C 44/44 PASS**, окремий Apache 2.4.58 без mod_deflate/mod_filter, syntax OK, private listener закрито. CSS fixture **4200→89 Б**, decoded SHA точний; MIME, Cache-Control і Last-Modified збережені. HEAD gzip: `Content-Length: 89`, порожнє тіло; сильні ETag різні для identity/gzip, обидва conditional ETag і Last-Modified дають 304 без тіла з правильним ETag/Vary. Apache не додає тіло або Content-Encoding у 304; Range та If-Range отримують identity. Перевірено gzip;q=0 і fallback, 404 для прямого `.gz` та відсутньої статики, PHP/Laravel-контроль та сторонній приватний vhost. Та сама секунда Last-Modified як у стандартного Apache: при публікації зміненого джерела не переносити час попередньої версії або використовувати нове хешоване ім'я.

## A/A та A/B/C: HTTP, CPU і пам'ять

Копії одного й того самого Apache 2.4.58, однакові шість SHA-пінованих реальних файлів і повністю завершені HTTP/1.1 відповіді. Для ізольованого A/B/C однакові завантажені модулі; тільки B використовує точний динамічний фільтр PERF‑27, тільки C використовує зовнішні sidecar через точний renderer, A — identity. Separate stock HTTP-contract доводить, що C не потребує deflate/filter. Для 1/3/5/10/20 паралельних GET по **24 хвилі/руку**, ABBA/BAAB для A/A та шість перестановок для A/B/C. Кодек/decoded SHA перевірено після завершення хвилі; C raw SHA/довжина збіглися з конкретним sidecar. Warm-up поза виміряними парами. Wire — HTTP-вхідний лічильник TCP клієнта (включає заголовки, але не TCP/IP overhead); Windows CPU/RSS — окремі процеси, RSS peak за життя, CPU квантується.

Історичний PERF‑27 не є поточним baseline: у A/A n=10 було **1566/1681 req/s** (парне відношення +7,0%), n=20 **2152/1942** (парне −5,2%). У контрольованому A/B/C: n=10 **1118 / 698 / 928 req/s**, тобто C швидше за B, але **−17,0% медіани і −19,8% парної медіани проти identity**. На n=20 **2219 / 1618 / 1359**: C **−38,7% медіани** проти identity і повільніше за B. На шести файлах A/B/C **330 596 / 62 920 / 63 008 Б**, C економить **80,94%**, не жертвуючи decoded пінами. Водночас сукупний CPU C **3328 мс** > B **2984 мс** > A **1203 мс**. За C процес Apache зафіксував **936 read operations / 51 572 976 Б**, рівно один повний оригінал на кожен виміряний запит; A/B облік таким способом читань не приростає (це не доказ відсутності mmap/cache I/O). Отже runtime-перевірка свіжості переносить витрату зі стиснення на перечитування й хешування. Apache `%D` є загальним service time, не чистим file-read latency. Додатковий позамережевий Node warm probe показав, що для CSS 155 КБ медіана читання оригіналу ~107 мкс, gzip ~75 мкс, перевірки пари ~270 мкс; ці числа не видаємо за дисковий latency Apache.

## Незалежний повтор C2 без послаблення перевірки

C2 залишив точний SHA вихідного файла, відсів symlink, справжні розміри обох репрезентацій і вже перевірене HTTP negotiation. Прибрав дубльоване `-f` там, де `filesize` уже доводить існування позитивної точної довжини, переніс окрему перевірку missing fallback після спроби віддати sidecar та об'єднав повторне зіставлення route/encoding. Другий stock HTTP smoke **44/44 PASS**. `perf28-ac2-01`: нові процеси з оберненим фізичним стартом, 24 хвилі/руку на 10 і 20, ABBA/BAAB, **1440** виміряних HTTP 200 з exact SHA; 36 primers виключені.

Ефект не зник: C2 дав лише **81,3% / 68,5% парної продуктивності identity** на 10/20 паралельних, CPU **797→1359 мс**. Нова серія на тій самій машині має інший абсолютний rps, тому не вибираємо C2 за прямим порівнянням із числом C з попередньої серії. Як і C, C2 виконує один повний логічний read оригіналу на запит. C2 лишається приватним експериментом, не частиною кандидата для публікації.

## Chromium на шести реальних сторінках

`perf28-browser02`: **48/48 HTTP 200**, **24/24** точні A/C пари нормалізованого HTML і payload (повний масив, включно з UUID, порядком, відповідями й підказками); винятки нормалізації — лише приватні порт/CSRF/Livewire URL. ## Локальна активація і точний відкат

**Активний `gramlyze.loc` не змінено.** Причина — повторене падіння пропускної здатності, а не відсутність модулів або доступу до консолі. Приватна копія ефективної конфігурації з точними XAMPP preimages і підключенням C лише з двох Gramlyze vhost, `shadow-final-c02`, пройшла `httpd.exe -t` / `Syntax OK`; вона не запускає та не перезавантажує службу. Перший shadow helper зупинився до запуску `-t`, коли припущення щодо лапок у двох Include не збіглося з пінованими байтами; повтор замінює тільки фактичні директиви. Не змінюємо глобальні файли, Gramlyze include, `.htaccess` та оригінали, не публікуємо sidecar у live і не перечитуємо службу. Приватний контроль другого vhost пройшов; замір «після застосування на живому Apache» тут не заявляється.

Фінально повторно підтверджено всі сім передстартових SHA, повний `verify` для 21 вихідного ресурсу та 15 gzip. На живому хості read-only CSS HEAD із пропозицією gzip завершився **HTTP/1.1 200, `text/css`, `Content-Length: 123022`, без Content-Encoding**. Перший заголовковий shell-wrapper помилково застосував перевірку статусу до кожного рядка заголовків і повернув exit 1 попри ті самі отримані заголовки; точна перевірка окремого status line завершилася exit 0.

[Інструкція з immutable покоління, preimage/SHA й відкату](../operations/perf-28-precompressed-static-assets.md) зафіксувала відтворюваний процес. Відкат live не потрібний — конфігурація не замінювалася. Для наступної спроби продуктивний шлях — **атомарно публікувати захищену незмінну пару identity+gzip** разом із manifest і окремо визначити долю стабільно названих JS/SVG. Це дозволило б не читати змінюваний оригінал перед кожною відповіддю, але потребує окремого дизайну публікації та повторного виміру. У цій роботі не підміняємо SHA перевіркою лише розміру/mtime.
