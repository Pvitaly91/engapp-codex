# PERF‑21 — автопідказки ручного введення у Step Easy

Перевірено 21 листопада 2026 року. База A — PERF‑20, `15469705691128517e29160ab4cb14707748f9f6`; B — зміна шаблона Step Easy в гілці `codex/perf-21-step-manual-autocomplete`.

## Зміна

Раніше кожен ввід із двох символів одразу викликав `/api/word-search/uk`. Перевірка покоління після розбору JSON відкидала частину застарілих відповідей, але не зменшувала кількість запитів і не прибирала попередній список одразу.

Тепер кожен ввід одразу зберігає чернетку, закриває попередній список, скасовує таймер і через `AbortController` скасовує активний `fetch`. Якщо після обрізання зовнішніх пробілів залишилося щонайменше два символи, новий запит починається через 250 мс тиші. Після `fetch` і повторно після `response.json()` перевіряються покоління та ідентичність пошуку, об'єкта питання, пропуску, слова, тексту й сфокусованого DOM-поля. Тому повернення до питання з тим самим індексом і текстом не відновлює стару відповідь. `AbortError` не показується як помилка.

Escape, втрата фокуса, вибір підказки, Enter, зміна слова чи пропуску, повторне відображення питання, завершення, навігація й restart очищають відповідний пошук. Відкладене фокусування не може захопити поле з наступного рендера. Таймери й контролери існують лише в компоненті. Поля стану й негайний виклик `persistState` залишилися; підказки попереднього поля не відновлюються після reload. Правила оцінювання, робота клавіш, API, розмітка, стилі та пошук у шапці (PERF‑15) не змінені.

## Контрольовані A/B-сценарії

Виконано inline JS точних A та B з реальними обробниками вводу й оновленням DOM у JSDOM, під керованим годинником і з mock `fetch`. «Відповіді» — успішно розв'язані проміси `fetch`; «JSON» — завершені розбори; «UI» — реально показані результати. Час — від останнього вводу актуального рядка до початку відповідного `fetch`, без серверної затримки.

| Сценарій | `fetch` A → B | Сигнали abort A → B | Відповіді A → B | JSON A → B | UI A → B | До запиту, мс A → B |
|---|---:|---:|---:|---:|---:|---:|
| `en → eng → engl → engli → englis → english`, 65 мс | 6 → 1 | 0 → 0 | 6 → 1 | 6 → 1 | 1 → 1 | 0 → 250 |
| Повільний ввід, 400 мс | 3 → 3 | 0 → 0 | 3 → 3 | 3 → 3 | 3 → 3 | 0 → 250 |
| Очищення до 250 мс | 1 → 0 | 0 → 0 | 1 → 0 | 1 → 0 | 0 → 0 | — |
| Запізнілий `fetch`, транспорт ігнорує abort | 2 → 2 | 0 → 1 | 2 → 2 | 2 → 1 | 1 → 1 | 0 → 250 |
| Запізнілий JSON | 2 → 2 | 0 → 1 | 2 → 2 | 2 → 2 | 1 → 1 | 0 → 250 |
| Питання №1 → №2 → №1 | 3 → 3 | 0 → 2 | 3 → 3 | 3 → 1 | 1 → 1 | 0 → 250 |
| Транспорт повернув `AbortError` | 2 → 2 | 0 → 1 | 2 → 1 | 2 → 1 | 1 → 1 | 0 → 250 |
| Escape, потім новий пошук | 2 → 2 | 0 → 1 | 2 → 2 | 2 → 1 | 1 → 1 | 0 → 250 |
| Втрата фокуса до 250 мс | 1 → 0 | 0 → 0 | 1 → 0 | 1 → 0 | 0 → 0 | — |

У контрольованому швидкому сценарії — на 5 клієнтських викликів менше (≈83%). За повільного вводу всі три запити зберігаються; список застарілих підказок, який A залишав при двох наступних редагуваннях, B закриває одразу. Abort не доводить скасування серверної роботи. Час Apache, SQL та FPS не вимірювалися.
