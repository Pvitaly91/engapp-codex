# PERF‑27: як перевіряти й застосовувати стиснення Gramlyze

**Межі.** Це інструкція для оператора, не деплой. Стенд Apache і майбутній приклад Nginx окремі. Наявність конфігурації в Git не означає, що стиснення ввімкнено. Фактичні результати живого `gramlyze.loc`, стенда і рішення — у [звіті PERF‑27](../reports/perf-27-http-compression.md). `gramlyze.ub`, production, робоча БД і персональні сесії не є цілями цих дій.

## Межа стиснення

- Дозвіл починається з перевірених публічних статичних URL і наявного файла у public root. CSS, JS і SVG доречні; PNG, JPEG, WebP, AVIF, ZIP, gzip, шрифти й будь-які вже закодовані відповіді не додаємо. Кодек визначає вебсервер через `Accept-Encoding`; не встановлюємо `Content-Encoding` вручну.
- Не вмикаємо стиснення за самим MIME для Laravel. Навіть гостьова HTML-відповідь може містити CSRF у спільному layout; Card, Step і Compose також мають дані сесії. Back office, вхід, прогрес, Livewire, сторінки з відображеним введенням, помилки та редиректи поза дозволеним набором незалежно від наявності Cookie в запиті. HTTPS цього ризику не усуває.
- Потенційні окремі динамічні винятки — рівно `/sitemap.xml` або конкретний публічний JSON, якщо для обох форматів у цільовому оточенні доведено відсутність секретів, авторизації, stateful middleware, сесійних cookies і відображених значень, а також відомий початковий розмір. Наприклад, у поточному коді словникове `/api/word-search/{uk|en|pl}` є окремим stateless API з публічними полями, але малі відповіді та шлях обробки помилок потрібно перевіряти на дроті. `/sitemap.xml` проходить через Laravel `web` middleware, тому залишити його поза конфігурацією за замовчуванням, навіть якщо XML-шаблон публічний. Не переносити рішення на весь `/api/` або всі `.xml`.

## Apache: локальний vhost

1. Звірити саме активний процес, його `ServerRoot`, `-f` і всі `Include`, entry для `gramlyze.loc`, public root та PHP handler. Для XAMPP з перевіреним стандартним коренем read-only команди нижче показують конфігурацію **на диску**. Зіставити її з процесом і перевірками по HTTP; `-M` не є доказом, що запущений процес уже перезавантажив ці байти.

   ```powershell
   $root = 'C:/Program Files/xampp/apache'
   $httpd = Join-Path $root 'bin/httpd.exe'
   & $httpd -d $root -f 'conf/httpd.conf' -S
   & $httpd -d $root -f 'conf/httpd.conf' -M
   ```

2. Потрібні `deflate_module`, `filter_module` і `headers_module`. Якщо будь-якого з них немає, на цьому зупинити **активацію**, не ставити непомітний `<IfModule>`-fallback і не редагувати спільний `httpd.conf`. Apache не завантажує `LoadModule` усередині `VirtualHost`; наявність DLL або можливість завантажити її на окремому loopback-стенді не означає доступності в живому процесі. Глобальне завантаження потребує окремої авторизації та плану перевірки інших vhost. Не використовувати Laravel, ручний заголовок чи інший PHP handler як обхід.
3. Якщо модулі вже доступні та є окремо перевірений дозвіл на застосування, перевірити [фрагмент Apache](../../tools/perf/http-compression/gramlyze-apache-gzip.conf) і підключити його **лише** всередині підтвердженого vhost. Зафіксувати SHA‑256 усіх файлів, що змінюються, точні вихідні байти в приватній копії поза public root і Git та окремо запам’ятати нові файли, яких до зміни не існувало. Не замінювати весь спільний vhost файл історичним snapshot. Після підготовки candidate використовувати `& $httpd -d $root -f 'conf/httpd.conf' -t`; за будь-якої помилки або неочікуваної зміни відповідного блоку відкотити до reload.
4. Graceful reload — лише підтримуваним способом для фактичного Apache процесу/служби, після успішної синтаксичної перевірки. Не використовувати stop/start замість graceful та не зупиняти чужих процесів. Якщо існуючий Windows startup-mode не дає підтвердженого graceful способу, відкласти застосування.
5. Після дозволеного застосування перевірити HTTP-докази нижче та контрольні відповіді інших локальних vhost **порівняно з їхнім власним ізольованим baseline**. Не редагувати їх конфігурації. Не зараховувати синтаксичну перевірку або простий Apache status 200 за підтвердження encoding.
6. Rollback: якщо перевірка не пройшла, припинити зміни. Відновити точні початкові байти змінених локальних конфігурацій, **лише** якщо поточні файли все ще збігаються з SHA запланованого кандидата; при сторонньому drift зупинитися та узгодити відновлення, не перезаписувати чужі зміни. Прибрати тільки новий фрагмент, створений для цієї активації, якщо він не існував у baseline. Звірити baseline SHA‑256, `-t`, підтримуваний reload і повернення початкових HTTP-заголовків на Gramlyze та контрольних vhost.

## Nginx: приклад для окремого майбутнього приймання

[Фрагмент Nginx](../../tools/perf/http-compression/gramlyze-nginx-gzip.example.conf) навмисно консервативний: `gzip off` за замовчуванням у цільовому vhost, одна статична allowlist для перевірених Vite-артефактів і двох SVG, початковий поріг **1024 Б** та рівень **6**. Ці початкові значення не є заміром Nginx. Точні Vite-імена взято з локального manifest; перед використанням звірити файл та SHA кожного з **цільовим** release manifest, узгодити його з уже наявним статичним handler. Відсутній файл має бути 404, не Laravel fallback. Не замінювати на шаблон для довільного `/build`, `/storage` або розширення.

- Перевірити `nginx -V` і повну ефективну конфігурацію `nginx -T` у приватному оточенні. Не комітити вивід `-T`: він може містити конфіденційні параметри. Окремо звірити precedence існуючих `location`, `root` / `alias`, symlinks нижче document root, MIME таблицю, редиректи, HTTPS/SNI, директиви доступу, `expires` і заголовки. Якщо існуючий static block визначає політику доступу або кешу, інтегрувати директиви в нього лише після перевірки еквівалентності; не ставити додатковий regex-location поперед захищеного шляху.
- Nginx може стискати `403` та `404` у gzip-enabled location. Приклад скеровує ці два статуси до окремих identity handler з тими самими статусами. Якщо цільовий сайт має власні тіла або маршрути помилок, зберегти їхній чинний вивід через наявні gzip-off handler замість прямого копіювання цих `return`-блоків. [Реалізація фільтра Nginx](https://github.com/nginx/nginx/blob/master/src/http/modules/ngx_http_gzip_filter_module.c)
- `gzip_min_length` використовує вихідний `Content-Length`. Звідси не випливає, що потокові відповіді без нього будуть відсіяні. Не поширювати цей фрагмент на потоки або динамічні маршрути. `gzip_types` **не** виключає `text/html`; безпека тут залежить від обмеження location до фізичних статичних файлів. [Документація Nginx gzip](https://nginx.org/en/docs/http/ngx_http_gzip_module.html)
- `gzip_proxied off` залишає відповіді identity для запитів із `Via`; це не детектор усіх проксі та не правило авторизації. Звірити CDN, ingress, reverse proxy, upstream `Content-Encoding`, `gzip_static`, Brotli та кеш-ключі у всіх шарах — за невідомого стану залишити стиснення вимкненим; обрати один шар, не додавати `gzip_proxied any` заради тесту. Не змінювати проксі-заголовки, щоб обійти правило.
- Не змінювати TLS, cache policy, ETag або Last-Modified вручну. Не додавати до allowlist відповіді з `no-transform`, private/no-store або персональними cookies; фрагмент не є фільтром цих заголовків і покладається на попередню перевірку публічної статики. Не обіцяти окремий сильний ETag для gzip без перевірки фактичної версії. У фрагменті запити з `Range` залишаються identity; перевірити `206`, `Content-Range` та цілісність тіла. Якщо в аудиті з’ясується, що зовнішній шар змінює ETag чи кешування, вимагати окремого підтвердження відображення двох репрезентацій, не ховати розбіжність.
- У майбутньому застосовувати лише після окремого дозволу: зберегти SHA й точний preimage, перевірити `nginx -t` з чинним target prefix та config, зробити graceful reload підтримуваним сервісним механізмом і повторити мережеву перевірку. Якщо виявлено відхилення, попередній `server`/include відновити за тими самими guard-правилами, звірити SHA, синтаксис і runtime. У PERF‑27 ця конфігурація нікуди не встановлюється.

## Які результати фіксувати

- Автоматичний контракт Apache: `node tools/perf/http-compression/contract.cjs`. За потреби задайте `PERF27_APACHE_ROOT` для каталогу наявної інсталяції. Тест створює окремий тимчасовий loopback listener і контрольні файли, не завантажує застосунок або БД та не змінює активну службу.
- На придатному великому ресурсі зробити незалежні запити з `gzip`, `identity`, без `Accept-Encoding`, з непідтримуваним алгоритмом і з явним `gzip;q=0`. Зберегти HTTP-статус, `Vary`, один або відсутній `Content-Encoding`, `Cache-Control`, `Content-Length` за наявності, `Transfer-Encoding`, валідатори та заголовки діапазону — без cookies і токенів. Байти response body рахувати до gzip-декодування й окремо після нього; не прирівнювати їх до розміру всього TCP/TLS трафіку.
- Стиснене тіло перевірити декодуванням та SHA‑256 проти identity. Якщо закодовані байти йдуть chunked або через HTTP/2 без `Content-Length`, значення не підставляти: перевіряти повноту декодування. Сторінки у приватних сесіях порівнювати тільки за контрольованим станом; справжні відповіді користувачів не записувати в звіт.
- Звірити `HEAD` (тіла немає), conditional GET із валідатором відповідної репрезентації, `304` (тіла немає), identity Range, малі файли та вже стиснуті зображення. Apache `DeflateAlterETag AddSuffix` розрізняє репрезентації, але для gzip-валідатора конкретний Apache може відповісти повним `200`, не `304`. Окремо перевірити `If-Modified-Since` і identity ETag, не уніфіковувати сильний ETag для різних байтів. [Документація Apache mod_deflate](https://httpd.apache.org/docs/2.4/mod/mod_deflate.html#deflatealteretag)
- Для приймання HTML перевірити активні UK/EN/PL, перше питання, autocomplete, reload/restart/resume в приватній сесії та завантаження JS/CSS. Трафік стиснених статичних файлів і метрики сторінки не означають, що стискається сам HTML. Подробиці всіх позитивних, негативних і невиконаних перевірок лишаються у звіті.
