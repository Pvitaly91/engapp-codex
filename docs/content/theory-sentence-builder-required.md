# Обов’язковий конструктор речень у теорії

Кожна нова або SEO-модернізована сторінка теорії повинна містити внизу «Практики» вбудований конструктор речень із п’ятьма питаннями своєї теми. Він не замінюється авторськими inputs або посиланням на тест. Завдання не завершене, поки цей блок не підключено і не перевірено на реальній сторінці.

Це обов’язкове доповнення до [канонічного шаблону](theory-template.md), а не новий дизайн. Історичне формулювання «передбачений linked widget» не робить конструктор необов’язковим для нових або модернізованих сторінок. Заморожений шаблон та історичні checksum manifests не переписуються.

## Потрібний блок

Використовується чинний `resources/views/components/text-block-practice-questions.blade.php`. Еталон — [Past Perfect Continuous: Forms and Use](http://gramlyze.loc/theory/tenses/past-perfect-continuous/past-perfect-continuous-forms).

На кожній цільовій сторінці має бути один вбудований конструктор, який послідовно показує рівно п’ять різних тематичних питань `Question::TYPE_COMPOSE_TOKENS` (чинне значення — `4`). У свіжій тестовій сесії видно українську умову, лічильник `1/5`, банк англійських слів та область складання речення. П’ять питань — не п’ять копій компонента.

Авторські вправи, зокрема власні inputs із ручним введенням і токенами, зберігаються та рахуються окремо. Посилання на `/test`, картка тесту, інший тип питання або непорожній масив linked questions не замінюють цей конструктор. Самі заголовок, `data-sentence-builder` чи HTTP 200 не доводять повноти та видимості блока.

## Декларація цілі та тематичного банку

На початку пакета віднови точні цільові сторінки з чинних завершених реєстрів і versioned sources. Дедуплікуй за owner identity та canonical URL, а не за номером редакції чи схожою назвою уроку. Запланований, але не реалізований пакет не є завершеним.

Для кожної нової або модернізованої цілі зафіксуй у versioned даних пакета:

- точний owner identity, locale та canonical local URL;
- Page/category binding і practice block UUID, metadata та прийнятий body стан відповідно до чинного guard;
- точний тематичний bank seeder, потрібний тип `4` і чинний CEFR-рівень блока;
- джерело підключення `linked_practice` та очікуваний результат: один widget, п’ять унікальних придатних питань.

Незалежне очікування owner → тематичний банк реєструється в `docs/content/theory-sentence-builders/*.json`. Банк визначають із погодженого змісту та versioned джерел, не з питань, які matcher уже випадково повернув. Кожна нова ціль повинна мати власний підтверджений контракт, навіть коли підключення працює без змін.

Чинна схема контракту: `schema_version: 1`, масив `targets` із полями `identity`, `definition`, `local_url`, `level`, `bank_seeders`. Нового owner додають до окремого versioned contract JSON. Поточні catalog/discovery обслуговують погоджений UK-процес; інша локаль потребує окремо погодженого розширення контракту без послаблення UK guards. Невідповідна локаль не повинна мовчки пропускатися або отримувати PASS.

Використовуй чинний `linked_practice`, спільний `TextBlockToQuestionsMatcherService` і наявні перевірені підключення, зокрема `PracticeCompletionLinkedPractice` там, де він уже застосовний. Його скінченний історичний scope не є реєстром усіх майбутніх уроків. Не створюй окремий helper, Blade/CSS/JS або grader лише через новий номер M-пакета.

Підключення через theory links має зберігати послідовність добору: зв’язки блоків цієї сторінки → тип `4` → точний bank seeder → чинний CEFR filter → п’ять різних питань. Прямий зв’язок питання саме з practice UUID не обов’язковий, якщо штатний matcher підтверджує page-wide зв’язок. Не прибирай owner, locale, theme або level guards, щоб набрати потрібну кількість.

Чинний linked matcher застосовує exact CEFR filter лише для `A1`, `A2`, `B1`, `B2`, `C1`, `C2`. Діапазон для відображення, наприклад `A2–B1`, не є exact-фільтром. Не переписуй рівень і не розширюй добір заради п’яти результатів; зафіксуй фактично застосований фільтр.

Придатний пул може містити більше п’яти питань; компоненту передаються рівно п’ять. Не дублюй одне питання та не підставляй чужий банк. Якщо придатних питань справді бракує, додай лише відсутні тематичні завдання через чинний versioned процес, з окремим переглядом їхніх умов, відповідей і перекладів.

## Застосування без сторонніх змін

Спочатку встанови фактичний served application/document root `gramlyze.loc` і звір потрібні власні файли з робочою гілкою. Наявність коміту або файлів іншого worktree не доводить, що їх використовує сайт. Якщо необхідний файл відсутній у served ROOT, перенеси тільки погоджені власні hunks, зберігаючи сторонню роботу.

Якщо конструктор уже підключений, отримує потрібні питання й видимий, залиш його без змін. Для точного підтвердженого стану допустима render-only проєкція без мутації початкової моделі та без запису в БД. Caller-owned межа теорії обов’язкова: курси й окремі тести не отримують нової поведінки автоматично.

Запис до робочої локальної БД потрібний лише тоді, коли проблему не вирішує коректне наявне підключення: точний preview → перегляд diff → exclusive backup → scoped transactional apply → postconditions → повторний no-op. Зберігай наявні відповіді, зв’язки поза ціллю та особистий прогрес. Не запускай масовий reseed, автоматичні HTTP/startup/scheduler записи або очищення кешів заради приховування проблеми.

Frozen releases, їхні raw bytes і guards залишаються чинними. Новий прийнятий стан оформлюється окремим доповненням або новою версією з точними source bindings; старі manifests не переписуються й guards не послаблюються. Навчальні тексти, авторська практика, details, metadata, URL, anchors, курси та дизайн компонента не змінюються цим підключенням.

## Регресійний захист для наступних пакетів

Спільна перевірка — `App\Support\TheorySentenceBuilderAcceptance`, регресії — `tests/Feature/TheorySentenceBuilderAcceptanceTest.php`. Реєстр цілей поєднує початкові 70 сторінок із discovery завершених `database/content-patches` за точними target identity/path та прийнятим AFTER. Новий знайдений owner без bank contract або конфігурації повинен спричинити помилку, а не зникнути з coverage. Discovery й acceptance не виконують apply та не створюють питань автоматично.

Перевірка має використовувати спільний механізм і актуальні цільові декларації, а не назавжди зашитий список поточних 70 сторінок. Додавання завершеної цілі наступного пакета повинно включати її до перевірки; відсутня декларація або відсутнє підключення не можуть мовчки виключити сторінку з coverage.

Для кожної цілі перевіряються:

- підключення існує й належить точним owner/locale/practice block;
- matcher повертає рівно п’ять унікальних питань потрібного типу, банку й рівня;
- компонент отримав саме ці питання, а серверний HTML містить рівно один native sentence builder;
- інша locale, чужий owner/банк, змінений binding і non-theory caller не отримують непогодженого підключення.

Негативні cases мають виявляти відсутню конфігурацію, порожній пул, менше п’яти придатних питань, неправильний тип, чужу тему, повторені question IDs та дубльований компонент. Не підмінюй matcher fixture довільною п’ятіркою й не послаблюй guards для зеленого тесту. Ізольовані тести не повинні завантажувати робочу `.env`, писати в робочу БД або змінювати питання чи прогрес користувачів.

Запускай явний read-only аудит із перевіреного served ROOT:

```sh
php artisan theory:audit-sentence-builders --target=gramlyze.loc
```

Для одного пакета додай `--source=approved-package.v1.json`, замінивши basename на точний файл погодженого versioned content patch. Команда перевіряє ROOT/loopback guard, використовує read-only транзакцію з rollback та свіжі локальні GET; вона не виконує apply. Результат стосується model/matcher/server HTML, а `browser_visibility` та `interaction` залишаються `not_checked`. AFTER-джерело ще не застосованого пакета створює незавершену перевірку готовності, а не доказ завершеної модернізації.

## Приймання реальної сторінки

1. Зроби свіжий GET точного URL на `http://gramlyze.loc`. Запиши кінцевий URL, статус і locale; редирект або HTML іншої сторінки не є успіхом.
2. Звір Page/practice binding, opt-in і чинний matcher. Зафіксуй bank seeder, придатний пул, фактичні п’ять IDs, типи та рівні. Відсутні в public HTML поля підтверджуй окремою дозволеною read-only перевіркою, а не припущенням.
3. Звір серверний компонент і його payload: один widget, п’ять унікальних питань типу `4`, правильна тема. Не приймай лише слово «Побудуй речення» або marker за достатній доказ.
4. Відкрий низ «Практики» у дозволеній браузерній сесії: картку видно без admin/debug режиму, є українська умова, лічильник, банк слів та область відповіді; JS-помилка не залишає порожню оболонку.
5. Для зміненого підключення перевір базову взаємодію: складання відповіді та перехід до наступного питання. Використовуй безпечну ізольовану тестову сесію; не очищай і не перезаписуй особистий localStorage, cookies, збережені відповіді або прогрес користувача.
6. Окремо запиши server presence, browser visibility та interaction checked/not checked для кожного URL. Познач неперевірені сторінки й конкретну причину обмеження, а не загальний PASS.

Не потрібно обов’язково проходити всі п’ять відповідей на кожній сторінці або всі 350 відповідей поточного набору, щоб підключити відсутній блок. Рівень перевірки має відповідати зміні; непроведений повний answer run не заперечує доведену наявність. Водночас HTTP payload не замінює перевірку видимості. Якщо браузер недоступний, не став visible PASS і не оголошуй цей крок завершеним.

Дотримуйся чинних computer-use правил і URL guard, не змінюй масштаб браузера та не обходь захист. Production, налаштування серверів і deployment не входять у цю процедуру без окремого дозволу.

## Умова завершення

У поурочному звіті наведи: URL → блок був/був відсутній → що змінено → фактичний server/browser/interaction результат. Повтори перевірку всіх погоджених цілей після виправлень. Не називай список відсутніх порожнім, доки частина scope не перевірена.

Закриття SEO-етапу потребує підключеного конструктора та підтвердження на реальній сторінці. Документована технічна недоступність чесно залишає конкретний крок незавершеним; код, commit або fixture не підмінюють live-приймання.
